# sync.sh 设计说明与踩过的坑

修改 `templates/sync.sh` 或某个项目里的 `<WORK>/sync/sync.sh` 之前先读这份说明。改完必须跑一遍
`bash scripts/test_sync.sh <脚本路径>`，确认全部通过。下面每一条都是第一次配置时实际遇到过的问题。

## 总体模型

- **本地是主副本**，远端是镜像。推送用 `--delete`，让远端与本地一致。
- **CC 的产出靠清单识别**。每次同步结束，在远端写 `$WORK/.sync-manifest`（路径、大小、修改时间），
  之后与清单不一致的文件就是 CC 新建或修改的。同步时先把这些文件拉回本地，再推送。
- **远端的 stamp 只是首次同步前的基线**。初始化时在写任何文件之前先 `touch $WORK/.sync-stamp`，
  首次同步写出清单后再删掉它。本地的 `$WORK/.sync-stamp` 一直保留，记录上次同步的时间。
- **职责分开**：`AGENTS.md` 是项目规则的唯一来源，只在本地改，推到远端供 CC 只读参考（`PUSH_ONLY`：远端的改动不拉回，推送时提示并用本地版本覆盖）。
  `CLAUDE.md` 两边各自维护，两个方向都排除。`$WORK/handoff/` 只从远端拉回本地。被排除的路径在接收端也受保护，`--delete` 不会删掉它们。

## 设计决定和原因

| 决定 | 原因 / 曾经的问题 |
| --- | --- |
| 用清单比"是否相同"，不用 `find -newer stamp` 比先后 | 第一版用修改时间比先后。两台机器时钟有偏差，或文件修改时间在未来（比如来自时钟偏快的 GPU 服务器），都会把没改过的文件误认成 CC 的改动，还会报出假冲突 |
| 拉回前用 `rsync -n -i --checksum` 按内容过滤 | 只是时间变了、内容相同的文件不算改动，比如用户 `scp` 取回脚本后修改时间不同 |
| 首次同步（本地还没有 stamp）时，同名不同内容的文件直接停下 | 代码审查时发现的缺口：旧逻辑会直接覆盖本地文件，只做了备份，脚本照常继续 |
| 用 `-rlt --executability`，不用 `-a` | `-a` 会同步权限位和属组，Mac 和 Linux 之间这两项天然对不上，预演里会冒出上万个"有变化"的文件 |
| `--exclude=.git` 不加开头的 `/` | 研究目录里的外部仓库各自带 `.git`。只排除根目录的 `.git` 时，会把上千个嵌套 `.git` 文件推上去 |
| 排除 `/$WORK/handoff/` | 本地没有 handoff 目录，不排除的话 `--delete` 会删掉远端（哪怕是空的）handoff 目录 |
| `AGENTS.md` 推送但不拉回（`PUSH_ONLY`），`CLAUDE.md` 两个方向都排除 | CC 需要读到完整的项目约定，但规则只能有一个编辑方：按普通文件处理的话，CC 一改就会被当成它的产出拉回本地，覆盖主副本。是否改过按内容判断（和其他文件一样走 `--checksum`），只改了修改时间不提示。本地的 `CLAUDE.md` 常是指向 `AGENTS.md` 的软链，推上去会顶掉远端的角色规则 |
| `--max-size` 兜底 | 扩展名列表挡不住所有权重和数据（如 `.bin`、`.npy`）。`--max-size` 只影响传输，不影响删除判断 |
| 预演时用 `--filter='. -'` 给待拉回的文件加 `-`、给它们的父目录加 `P` | 预演时还没有真正拉回，推送预览会把 CC 新建的目录显示成"删除"，很吓人 |
| 推送只打印汇总（新增 / 大小变化 / 仅修改时间 / 删除），明细写日志 | 首次预演可能有上万行，用户看不过来。要删除的文件单独列出，因为删除风险最大 |
| CC 删除的文件会被提示并恢复 | CLAUDE.md 不允许 CC 删除文件；万一删了，推送会从本地恢复，同时给出提示 |
| `SANITY` 文件检查 | 推送带 `--delete`。如果在错误的目录运行，可能把远端的整份副本清空 |

## shell 兼容性的坑

- **SIGPIPE**：在 `set -o pipefail` 下，`cmd | head -1` 会让 `cmd` 收到 SIGPIPE，脚本以退出码 141 中途退出。
  取第一行用 `${var%%$'\n'*}`，取前 N 行用 `awk 'n++ < N'`。测试里不要写 `sync.sh | grep -q`，要先取完整输出再匹配。
- **macOS 自带 openrsync**：它缺 `--files-from`、`--backup-dir` 等功能，脚本检测到会拒绝运行，提示用户 `brew install rsync`。
  老的 Apple rsync 2.6.9 里 `-E` 表示扩展属性，所以可执行位一律写成长选项 `--executability`。
- **macOS 的 bash 3.2**：没有关联数组；`set -u` 下空数组展开会报错，所以冲突列表用字符串拼接；`-nt` 只精确到秒。
- **itemize 标记**：推到远端时传输行以 `<f` 开头，本机模式（测试用）是 `>f`，所以计数时两种都要认。
- **远端命令**：用 `ssh host "cd dir && bash -s" <<<"$REMOTE_LIB$cmd"` 执行，避免多层引号转义。
  远端有 GNU find，可以用 `-printf`；本地是 macOS 的 BSD find，没有 `-printf`，所以本地不做清单，只记 stamp。

## 测试

- `scripts/test_sync.sh <sync.sh>` 用本机模式（`SYNC_REMOTE=""`）在临时目录里模拟两端，覆盖：首次同步冲突、预演无副作用、
  各类排除项、`AGENTS.md` 只推不拉、`--delete`、清单、时钟偏差、真冲突与 `FORCE=1`、CC 删除文件后恢复、handoff 保护、汇总计数、在错误目录运行。
- 本机模式测不到 ssh 这一段。首次用于真实项目时，让用户在本地先跑 `-n` 预演，再正式同步。
