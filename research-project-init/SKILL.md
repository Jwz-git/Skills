# 科研项目初始化

这个技能产出两样东西：一份 `AGENTS.md`，一套研究目录约定。

- **`AGENTS.md`** 是项目规则的唯一来源，所有 Agent 都读它：本地的 Codex、软链过来的本地 Claude Code，以及远端只读的 Claude Code。它分两部分：
  - 「一、项目约定」：每个 Agent 都要遵守；
  - 「二、本地执行」：只由在主副本上运行实验的 Agent 执行。

  这样拆分，是为了让只读的 Agent 读到全文，也不会误以为自己该去跑实验。
- **研究目录约定**：研究放在 git 忽略的 `<WORK>/exp/` 里，按用途分组，效果好再抬升进主线。

骨架是 `templates/AGENTS.md.tmpl`，写法要点见文末。

## 先判断在哪里运行

| 情况 | 怎么认 | 怎么做 |
| --- | --- | --- |
| 本地主副本 | 项目根目录有 `.git` | 直接写 `AGENTS.md`，建研究目录 |
| 远端镜像（配合 remote-cc-collab 的项目） | 没有 `.git`，有 `<WORK>/.sync-manifest` 或 `<WORK>/.sync-stamp` | 不直接写 `AGENTS.md`：它只从本地推过来，在这里写会被覆盖，本地没有时还会被删掉。研究目录和索引也不直接建。全部写成交接，由本地 Agent 落地 |
| 刚拷到远端、还没配同步 | 没有 `.git`，也没有上面两个文件 | 先用 remote-cc-collab 建同步基线（它要求在写任何文件之前先建），再回来 |

如果用户说的是个人项目或普通软件项目，告诉他们不需要这套流程。

## 步骤

### 1. 确认参数

先从用户的话和项目文件里推断，推断不出来的再问：

- **项目名**。
- **研究目录 `WORK`**：默认 `temp`，必须已被 `.gitignore` 忽略。否则研究文件会出现在 `git status` 里，迟早被误提交。
- **只留本地、不进 git 的东西**：参照 `.gitignore`，如 `paper/`、`log.md`、`AGENTS.md`。
- **已有的 `AGENTS.md`、`CLAUDE.md`**：有没有，`CLAUDE.md` 是不是指向 `AGENTS.md` 的软链。在远端镜像上，`AGENTS.md` 如果已经推过来了，就能读到。
- **时区**：用于"预计完成时间"。

### 2. 了解项目

依次阅读：
- `README` 和复现文档；
- `.gitignore`；
- 研究目录的索引和命名约定；
- smoke 或小规模验证的定义；
- 基线结果的摘要；
- 以往的抬升记录；
- 文档里出现的 GPU 服务器路径和环境说明。

用几句话向用户汇报：主线是什么、研究目录怎么组织、最近在做什么、哪些信息还缺。这一步也是在核对你的理解。

### 3. 起草 `AGENTS.md`

以 `templates/AGENTS.md.tmpl` 为骨架，把第 2 步弄清的内容填进去。拿不准的保留 `<尖括号>` 占位符，在汇报里列出来，不要猜。

- **新项目**：按模板写，删掉不适用的行和节。
- **已有 `AGENTS.md`**：不要整体替换。按下面的写法要点逐节检查，把原有内容归入「一」「二」，补上缺的节，修掉有问题的条目。给用户的汇报里，把改动按"移动 / 改写 / 新增 / 删除"列出来，删除的条目写明原因。

项目如果配合远端 Claude Code 使用，把 remote-cc-collab 的 `templates/AGENTS-section.md.tmpl` 填好，放进「二、本地执行」的开头。

### 4. 研究目录

沿用项目已有的约定。没有约定时，建 `<WORK>/exp/` 下的 `experiments/`、`analysis/`、`research/`、`maintenance/`、`output/`，再写一份 `<WORK>/exp/README.md` 当索引：说明每个分组放什么、新目录怎么命名、每条登记写哪些字段。

### 5. 落地

- **本地主副本**：直接写 `AGENTS.md` 和研究目录。用户如果在本地也用 Claude Code，建议执行 `ln -s AGENTS.md CLAUDE.md`，两边读同一份规则。确认 `CLAUDE.md` 也被 `.gitignore` 忽略。
- **远端镜像**：写 `<WORK>/handoff/<YYYYMMDD-HHMM>-setup-agents.md`，格式按远端 `CLAUDE.md` 的交接格式：
  - 「交给本地 Agent 的任务」：本地没有 `AGENTS.md` 时，按附录写；已有时，按附录和改动清单合并。剩下的占位符按本地实情填，拿不准的问用户。最后向用户汇报改了哪些节。
  - 「需要本地处理」：要新建的研究目录和索引文件，以及索引的内容。
  - 附录：`AGENTS.md` 的草稿全文。模板里有三个反引号的代码块，所以附录用四个反引号的代码块包住。

  本地 Agent 写好 `AGENTS.md` 之后再同步一次，它才会推到远端；远端 `CLAUDE.md` 里的 `@AGENTS.md` 从那时起才生效。

### 6. 汇报

告诉用户：
- 写了什么，或者交接文件的路径；
- 还剩哪些占位符；
- 哪些原有条目被移动、改写或删除，以及原因。

## AGENTS.md 写法要点

这些是整理已有 `AGENTS.md` 时最常见的问题：

- **只写规则和现状，不写历史。** "自某日起……"、某次实查的结果、"已经移除了……"这类记录，过一阵就不准了，应该写进阶段记录。规则里只留它们推出来的现行约定。
- **「当前主线」只写不能弄错的口径。** 方法、影响结论的配置、入口、对照基线和数字，写到这些就够了。完整参数、全部脚本清单留在 README 和复现文档里，写两份迟早不一致。
- **按读者分开。** 跑实验、SSH、git、同步这类操作，一律放「二」。「一」只写所有 Agent 都适用的约定，因为只读的 Agent 也会读到全文。规则放进对应的节，不要追加在文件末尾，也不要混进不相关的节（比如把训练规则写进"沟通"）。
- **服务器只记 SSH 别名。** host、port 以 `~/.ssh/config` 为准。文件里写死地址既会过期，也会把地址带到每台同步过去的机器上。私钥、口令和 token 一律不写。
- **rsync 到 GPU 服务器的示例要能直接用。** 源目录不带结尾的 `/`，否则目录里的内容会摊到目标根目录；不用 `--delete`；排除 `.git/`。
- **每条规则都说得出原因**，或者说得出它防止哪种失败。说不清的规则，和说不清的 guard 一样，不写。
- **交接、同步相关的条目以 remote-cc-collab 的片段为准。** 旧项目里手写的同步说明，常常已经和脚本的实际行为对不上。
