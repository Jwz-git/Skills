# 科研项目初始化

给科研项目配好两样基础的东西：

- **`AGENTS.md`**：项目规则的唯一来源，不进 git。它分两部分：
  - 「一、项目约定」：所有 Agent 都遵守；
  - 「二、本地执行」：只由在本地主副本上跑实验的 Agent 执行。

  这样分，是为了让只读参考规则的 Agent 读到全文，也不会以为自己该去跑实验。比如以后用 remote-cc-collab 接入的远端 Claude Code，读的就是这同一份文件。
- **研究目录**：研究放在被 git 忽略的 `<WORK>/exp/` 里，按用途分组，在一份索引里登记，效果好再抬升进主线。

骨架是 `templates/AGENTS.md.tmpl`，写法要点见文末。

本技能只做基础配置。项目要和远端的 Claude Code 协作时，初始化完成后再用 remote-cc-collab 补上协作内容：同步脚本、远端的 `CLAUDE.md`、交接目录，以及 `AGENTS.md` 里的协作一节。

如果用户说的是个人项目或普通软件项目，告诉他们不需要这套流程。

## 在哪里运行

在项目的本地主副本里运行，也就是项目根目录有 `.git` 的那一份。

没有 `.git` 的目录多半是远端的副本。`AGENTS.md` 只在本地维护，在副本里写的会在同步时被本地版本覆盖，本地没有这个文件时还会被删掉。所以不要在副本里写 `AGENTS.md`，也不要建研究目录，而是告诉用户到本地主副本里运行本技能。用户要求就在这里起草时：
- 已经用 remote-cc-collab 配好同步的副本，按那里 `CLAUDE.md` 的规则，把草稿写成交接；
- 其他情况，把草稿直接放在回复里，由用户转给本地 Agent，不在副本里留文件。

## 步骤

### 1. 确认参数

先从用户的话和项目文件里推断，推断不出来的再问：

- **项目名**。
- **研究目录 `WORK`**：默认 `temp`。
- **只留本地、不进 git 的东西**：参照 `.gitignore`，如 `paper/`、`log.md`。
- **已有的 `AGENTS.md`、`CLAUDE.md`**：有没有；`CLAUDE.md` 是不是指向 `AGENTS.md` 的软链。
- **时区**：用于"预计完成时间"。

### 2. 了解项目

依次阅读：
- `README` 和复现文档；
- `.gitignore`；
- 研究目录的索引和命名约定；
- smoke 或小规模验证的定义；
- 基线结果的摘要；
- 以往的抬升记录；
- 文档里出现的 GPU 服务器路径和环境说明。

用几句话向用户汇报：主线是什么、研究目录怎么组织、最近在做什么、哪些信息还缺。这一步也是在核对你的理解。

### 3. 写 `AGENTS.md`

以 `templates/AGENTS.md.tmpl` 为骨架，把第 2 步弄清的内容填进去。拿不准的保留 `<尖括号>` 占位符，在汇报里列出来，不要猜。

- **新项目**：按模板写，删掉不适用的行和节。
- **已有 `AGENTS.md`**：不要整体替换。按下面的写法要点逐节检查，把原有内容归入「一」「二」，补上缺的节，修掉有问题的条目。
  - 动手前先把原文件复制到 `<WORK>/exp/maintenance/<名称>/`：`AGENTS.md` 不在 git 里，覆盖了就找不回来。
  - 改动按"移动 / 改写 / 新增 / 删除"列出来，删除的条目写明原因。清单写进同一个目录，也放进给用户的汇报。

### 4. 建研究目录

沿用项目已有的约定，不搬动已有的目录。没有约定时，建 `<WORK>/exp/` 下的 `experiments/`、`analysis/`、`research/`、`maintenance/`、`output/`，再写一份 `<WORK>/exp/README.md` 当索引：说明每个分组放什么、新目录怎么命名、每条登记写哪些字段。

### 5. 收尾

- **`.gitignore`**：确认 `<WORK>/`、`AGENTS.md`、`CLAUDE.md` 都被忽略。缺的补上，并告诉用户：这是一处 git 改动，由用户决定什么时候提交。
- **本地的 `CLAUDE.md`**：用户在本地也用 Claude Code 时，建议执行 `ln -s AGENTS.md CLAUDE.md`，两边读同一份规则。已有的 `CLAUDE.md` 不是软链时，先把其中的项目规则并进 `AGENTS.md`，再问用户要不要换成软链。
- **核对**：运行 `git status --short`。这次新写的文件都不应该出现在里面，出现了说明忽略规则没配好。

### 6. 汇报

告诉用户：
- 写了哪些文件、建了哪些目录；
- 还剩哪些占位符；
- 原有条目的移动、改写和删除，以及原因、原文件的备份位置；
- 项目要和远端 Claude Code 协作的话，下一步用 remote-cc-collab。

## AGENTS.md 写法要点

这些是整理已有 `AGENTS.md` 时最常见的问题：

- **只写规则和现状，不写历史。** "自某日起……"、某次实查的结果、"已经移除了……"这类记录，过一阵就不准了，应该写进阶段记录。规则里只留它们推出来的现行约定。
- **「当前主线」只写不能弄错的口径。** 方法、影响结论的配置、入口、对照基线和数字，写到这些就够了。完整参数、全部脚本清单留在 README 和复现文档里，写两份迟早不一致。
- **按读者分开。** 跑实验、SSH、git、同步这类操作，一律放「二」。「一」只写所有 Agent 都适用的约定，因为只读的 Agent 也会读到全文。规则放进对应的节，不要追加在文件末尾，也不要混进不相关的节（比如把训练规则写进"沟通"）。
- **服务器只记 SSH 别名。** host、port 以 `~/.ssh/config` 为准。文件里写死地址既会过期，也会把地址带到每台同步过去的机器上。私钥、口令和 token 一律不写。
- **rsync 到 GPU 服务器的示例要能直接用。** 源目录不带结尾的 `/`，否则目录里的内容会摊到目标根目录；不用 `--delete`；排除 `.git/`。
- **每条规则都说得出原因**，或者说得出它防止哪种失败。说不清的规则，和说不清的 guard 一样，不写。
- **和远端协作的旧说明不在这里改。** 手写的同步、交接说明原样归入「二」，在汇报里提醒用户用 remote-cc-collab 核对：这类说明常常已经和同步脚本的实际行为对不上。
