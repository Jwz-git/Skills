# 笔记更新指南

执行 `update` 模式时使用本文档。更新已有笔记应兼顾**过程透明**与**正文纯净**：对用户的变更交代放在对话回复里，笔记正文始终保持流畅、连贯、面向阅读，不堆积面向 AI 的审计补丁和流水账。

## 1. 默认更新方式：自然融合 + 对话透明交代

当发现事实错误、补充代码/附录核验细节，或加入新的理解时：

1. **直接融改正文**：在对应的正文章节中重写并理顺相关段落、表格或公式，使上下文语义连贯。
   - **禁止打补丁腔**：不要把“旧笔记此处写错，现核对修正为……”或与前句自相矛盾的补充句硬贴在原文后面，而应直接把正文改成准确表述。
   - **保留用户观点**：若笔记中已有用户本人写下的个人判断或批注，不要静默覆盖；当新证据与之冲突时，在对话中明确指出，并在取得确认或以自然措辞并列说明差异后更新。
2. **在对话回复中透明汇报变更**：每次更新后，向用户简要说明修改了哪些章节、原表述与新表述的实质差异，以及修改依据（论文章节、公式、表格或代码文件）。
3. **默认不追加文末更新日志表**：常规更新不再强制在笔记末尾生成「理解更新记录」以及 `原理解 / 新理解 / 状态：confirmed` 这类机器格式审计表，也绝不把“由 AI 生成”“依据某规范重构”“论文命名核验”等工具维护流水账写进正文。

## 2. 仅在明确需要时保留简短演变记录

只有满足以下任一条件时，才在笔记末尾保留简洁的演变说明：

- 用户明确要求在笔记正文中记录理解演变史；
- 目标笔记已存在用户本人长期维护的个人更新日志（此时沿用其现有风格，不强行覆盖格式）。

即便记录，也只写对未来复习有意义的实质理解转变（日期 + 一两句自然中文），不使用机器状态键表，不记录纯格式调整。

## 3. 纯元数据与纯附件维护

### 元数据维护

只整理 `tags` 或其他 frontmatter 属性时：

- 只修改 frontmatter，不改动正文与文件名；
- 保留 profile 允许的既有元数据字段，不擅自删除 `aliases` 等未知字段；
- 在交付回复中汇总标签映射、修改文件数与 `audit_tags.py` 验证结果。

### 图片附件维护

只迁移图片、规范路径、重裁瑕疵图或清理重复/行内嵌图时：

- 执行 [论文图片附件规范](attachment-guide.md)；
- 不借附件维护之机改写论文事实论述、frontmatter 或标签；
- 在交付回复中汇报盘点基线、移动/重裁/修改数量、验证结果及保留未处理的例外。
